# 目标架构与迁移方案

## 1. 方案比较

### 方案 A：分阶段纵向迁移（采用）

先建立工具链和目录所有权，再迁移 shared/infrastructure/design，然后按“资源包内核 → 编辑器共享 UI → 业务编辑器 → 路由组合”切片。每阶段更新全部调用者并完成静态与运行时验证。

优点：

- 保护当前业务行为和工作区已有修改；
- 设计组件契约变化可逐个消化；
- 问题定位和回退范围小；
- 每个切片能形成独立审查门。

代价：迁移期短暂存在新旧目录。控制方式是不新增 forwarding barrel，每个切片完成后删除已迁移旧文件。

### 方案 B：一次性镜像后修复（不采用）

先复制全部适用基础目录，再批量移动业务代码和修复导入。它会同时破坏大量调用者，在无自动化测试的项目中难以区分结构、设计系统和业务回归。

### 方案 C：只更新 design 与依赖（不采用）

它无法完成“代码组织结构同步”，会继续保留技术层平铺、宽 barrel 和 DataContext 多职责。

## 2. 同步方法

非业务层采用“能力同源、业务适配”，不是整目录原样复制：

- 先由本项目目标调用者选定需要的 Design/theme/shared/browser 能力；
- 选中后以固定参考文件和最小依赖闭包为实现/行为基线；
- 只适配路径、ResourceEx 业务契约、部署环境和仓库约束；
- 不迁入无调用者的通用模块，不把账户、搜索、站点、服务端等参考业务伪装成基础层；
- 选中能力涉及的参考 `patches/*.patch` 原样复制，并按包名登记到 `pnpm.patchedDependencies`；
- 任何偏差先登记到 [10-非业务能力同步与偏差台账.md](./10-非业务能力同步与偏差台账.md)。

## 4. 所有权规则

- route 只组合 feature 入口，不持有实体增删改算法。
- `shared` 不依赖 `design`、`domain`、`features`、`infrastructure` 或 route。
- `domain` 不依赖 React、HeroUI、browser infrastructure 或 feature。
- `infrastructure` 不依赖 feature、design 或 route。
- `design` 不依赖 editor feature。
- `design/theme` 为 Tailwind/Prettier 外部工具加载，项目内 import 保持可解析相对路径。
- feature 可依赖 design、domain、infrastructure、shared，但不能反向依赖 route。
- `app/**` 同目录或子目录用 `./`，目录树外用 `@/`；不使用 `../`。
- 不创建仅为缩短路径的 `index.ts`。

根 `app/` 一旦存在就成为活动 App Router owner，因此不能先创建零散的 `app/design` 或 `app/domain` 再等待最后迁路由。首个结构切片必须同时建立可运行的根 `app/layout.tsx`、`providers.tsx`、根重定向和 12 个 route shell，并临时使用 `@/* -> ["./app/*", "./src/*"]`、双目录 TypeScript include 和 Tailwind content。新 owner 优先从 `app` 解析，尚未迁移的调用者回退到 `src`；全部 owner 迁完并删除 `src` 后，再收紧为单一 `./app/*`。过渡期每个切片都必须能构建，不能依赖“最终一起修”。

## 5. 核心边界

### Static export

- `next.config.ts` 无条件保持 `output: 'export'`；不复制参考项目按环境切换 export/standalone/Node runtime 的分支。
- App Router layout/page 可以保留构建时执行的 Server Component，但不能读取请求态、数据库、账户或运行时私密环境变量；所有交互与浏览器 API 都进入 client boundary。
- 不迁入 Server Action、请求相关 Route Handler、cookies、headers、rewrites、proxy、ISR、intercepting routes 或默认 `next/image` 优化服务。
- 根 `/` 继续由静态 `index.html` 中的客户端路由逻辑替换到 `/info`，不使用 Next 运行时 redirect。
- 保留现有 `next/font/google` 的 Noto Sans、Noto Sans Mono、Noto Sans SC 配置；原样迁入的 Next Patch 将构建期 Google Fonts CSS/字体请求改到镜像域名，构建产物仍自托管字体。
- 静态资源使用 origin-root 路径，不复制参考 CDN/assetPrefix 环境分支。
- 外部 Nginx/静态服务器负责 extensionless route → `.html`、404、缓存、压缩和响应头；应用不假定存在 Next Node server。

Next 官方静态导出能力与限制见 [Static Exports](https://nextjs.org/docs/app/guides/static-exports)。

### ResourceEx domain

负责：

- JSON 契约；
- parser-only wire 契约、外部数据结构验证与规范化状态；
- 旧格式归一化；
- 导出清理、排序、换行规范化；
- Label、ID 范围和引用规则。

不负责 React、JSZip、FileSaver、Blob URL、Web Crypto 或浏览器事件。

### Evaluation domain

`app/domain/evaluation/types.ts` 保留本项目 `TRatingKey` 联合类型。Design rating theme 与固定参考提交相同，依赖该 domain 叶子；不能把领域键反向声明在 Design 中。

### Resource editor feature

负责：

- ZIP adapter；
- asset Blob/URL 生命周期；
- ResourceEditor Provider；
- 导出校验 orchestration：组合 domain issues、资产快照与 browser 签名验签；
- 未保存状态；
- 编辑器共享表单；
- 12 个具体编辑器。

### Design

只保留参考设计系统中适用于本项目的叶子组件和主题能力。编辑器 Select 放入 resourceEditor feature，并以 HeroUI Select 为底层保留业务值契约；当前 Navbar 组合属于 appShell feature。高外观固定开启，不引入参考项目偏好 store。

### Infrastructure

基于参考失败处理原则、按目标调用面缩小的 `safeStorage` 和本项目 Web Crypto/PEM adapter 放在 browser infrastructure。最新浏览器目标下直接使用标准 `MediaQueryList.addEventListener`；两者都是调用者审计后登记的适配，不是任意简化。

## 6. 风险控制

| 风险                           | 控制                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| design 覆盖导致大量调用者破坏  | 先完成公开契约矩阵，再逐组件迁移                           |
| 草案 UI 被误当成业务不变量     | 以数据/流程结果为兼容基准，UI 按参考成熟模式验收           |
| DataContext 拆分改变序列化     | 用固定夹具比较 JSON、ZIP entry 和资产 SHA-256              |
| barrel 删除暴露循环依赖        | 叶子 import、逐文件依赖方向审查、每切片 tsc                |
| 依赖解析边界不透明             | 同时审查直接依赖与 public hoist；干净安装和构建验证        |
| 根 `app/` 过早接管导致路由缺失 | 先建立完整 route 过渡壳，临时 alias/include/content 双路径 |
| 依赖 patch 漏迁或内容漂移      | 原样复制相关 patch、按包名登记、安装后核对 lockfile        |
| 参考业务/服务端依赖误带入      | 每个依赖必须有本项目直接调用者和 owner；静态导出扫描兜底   |
| 同类非业务能力被草案实现弱化   | 参考文件优先、依赖闭包审查、所有偏差进入台账               |
| 为参考目录对称引入死代码       | 只有目标调用者或已选能力的依赖闭包才能触发迁入             |
| 旧浏览器兼容层误带入           | 明确排除 compat/polyfill/flexbugs/mediaQuery fallback      |
| 工作区已有修改被覆盖           | 阶段前后记录 status、staged diff 和 unstaged diff          |
| 大规模移动难审查               | 机械移动与行为调整分开记录                                 |
| 无测试套件                     | 确定性 archive 夹具 + 真实浏览器矩阵                       |

## 7. 固定设计

- Select 迁到 `features/resourceEditor/client/components/select`，底层使用 `@heroui/select`，保留编辑器值、分组、禁用和描述契约。
- Input 同步参考 Design wrapper；参考仓没有 Textarea wrapper，目标新增同 owner 的最小适配，二者底层均使用 `@heroui/input`。
- 依赖 patch 按 [11-依赖Patch迁移矩阵.md](./11-依赖Patch迁移矩阵.md) 原样复制；Select 不恢复 patch 移除的打开时自动滚动。
- `DesignPreferencesProvider` 固定 `isHighAppearance: true`，不新增设置 store。
- 原生 `alert`/`confirm` 改为 Popover、Modal 或内联反馈；`beforeunload` 例外。
- `IdRangeEditor` 的原生 `<dialog>` 迁为 Design Modal。
- 不保留旧目录 forwarding barrel，每个切片一次性更新调用者。
- layout 保留 `next/font/google` 的三组 Noto 字体、CSS 变量和 `<html>` className 接入；不迁入参考 `app/assets/fonts/**`。
- `next.patch` 按 [11-依赖 Patch 迁移矩阵](./11-依赖Patch迁移矩阵.md) 原样迁入；不得利用其中的 warning 降级引入 intercepting routes。
- 根页面保持客户端 `/` → `/info` 替换；外部静态服务器使用 `.html` fallback 提供 12 个直接访问路径。

代码实施必须获得独立授权；文档定稿本身不代表实施开始。
